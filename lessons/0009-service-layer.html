第 9 课：Service 层 -- 业务逻辑的家

预计用时：30 分钟 | 难度：中级 | 前置知识：第 7 课 条件构造器与分页查询、第 8 课 前后端联调

目标：给业务逻辑找个家

从这一课开始，进入工程化进阶阶段。前 8 课你的全栈链路已经跑通，但现在有一个架构隐患：Controller 直接操作 Mapper，查询条件、分页逻辑全堆在 Controller 里。

用你熟悉的前端类比：这就像在 Vue 组件的 @click 事件里直接写 axios 调用，还夹杂着各种业务判断 -- 小项目能跑，但业务逻辑一复杂就失控。你在前端是怎么解决的？分层：axios 调用抽进 api/user.js，共享业务逻辑抽进 Pinia store。后端也一样。

三层架构：Controller -> Service -> Mapper

这是 Java 后端最经典的分层模式，每一层职责单一：

浏览器 (Vue3 + axios)
     │ HTTP 请求 / JSON 响应
     ▼
┌─────────────────────────────────────────────────┐
│  Controller 层   @RestController                 │
│  职责：接收请求、参数绑定、返回 JSON                │
│  类比：Vue 组件的事件处理函数（@click -> 函数）     │
└───────────────────┬─────────────────────────────┘
                    │ 调用（依赖注入）
                    ▼
┌─────────────────────────────────────────────────┐
│  Service 层   @Service        <-- 今天的主角      │
│  职责：业务逻辑 -- 校验、计算、组合多次数据操作      │
│  类比：Pinia store 的 actions / composables      │
└───────────────────┬─────────────────────────────┘
                    │ 调用
                    ▼
┌─────────────────────────────────────────────────┐
│  Mapper 层   BaseMapper<User>                    │
│  职责：数据访问 -- 一个方法对应一条 SQL             │
│  类比：api/user.js 里封装的 axios 调用            │
└───────────────────┬─────────────────────────────┘
                    │ SQL
                    ▼
               PostgreSQL
分层 职责 前端类比 不该做什么
Controller HTTP 交互：收参数、返回 JSON Vue 组件事件处理 不写业务规则
Service 业务逻辑：校验、计算、组合调用 Pinia store actions 不关心 HTTP 细节
Mapper 数据访问：方法与 SQL 一一对应 api/user.js 不写业务判断

为什么业务逻辑不能放 Controller？

和你不会把复杂业务判断写在 Vue 组件的 @click 里是同一个道理：

  • 复用 -- 同一段业务规则（如"邮箱查重"）可能被多个入口使用：用户注册接口、后台管理接口、未来的定时任务。放 Service 层大家都能调，就像多个组件共享同一个 store action。
  • 测试 -- Service 是普通 Java 类，不依赖 HTTP，可以直接写单元测试，就像你单独测试 store action 而不用挂载组件。
  • 可维护 -- Controller 一眼看清有哪些 API，Service 一眼看清有哪些业务规则，各归其位。

第一步：创建 UserService 接口

MyBatis Plus 不只是提供了 BaseMapper，还提供了一套配套的 Service 层脚手架：IService 接口 + ServiceImpl 实现类。用法和 BaseMapper 一样 -- 继承就自动获得全套 CRUD 方法。

在 service 包下（com.yourname.demo.service）新建 UserService.java：

package com.yourname.demo.service;

import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.baomidou.mybatisplus.spring.service.IService;
import com.yourname.demo.entity.User;

public interface UserService extends IService<User> {

    // 自定义业务方法：分页 + 条件搜索（第 7 课写在 Controller 里的逻辑，搬到这里）
    Page<User> pageList(long page, long size, String name, String email);

    // 自定义业务方法：创建用户（内含业务规则，第四步实现）
    User createUser(User user);
}

注意两个要点：

  • extends IService<User> -- 自动获得 save()、getById()、page()、removeById() 等全套方法，不用声明、不用实现，和 UserMapper extends BaseMapper<User> 同理（见第 6 课）。
  • 只声明自定义业务方法 -- 通用 CRUD 已经白嫖了，接口里只写 BaseMapper/IService 没有的东西。

接口 + Impl：TypeScript 程序员不陌生

Java 的惯例是一个 Service 拆成两个文件：UserService（接口，定义契约）+ UserServiceImpl（实现类）。你在 TypeScript 里也这么干过：

interface UserService {           // 契约：有哪些方法
  pageList(...): Promise<Page<User>>
}
class UserServiceImpl implements UserService { ... }  // 实现

好处：Controller 只依赖接口，不关心实现。以后想换实现（比如测试时换成 mock），Controller 一行不用改。

第二步：创建 UserServiceImpl 实现类

同包下新建 UserServiceImpl.java：

package com.yourname.demo.service;

import com.baomidou.mybatisplus.core.conditions.query.LambdaQueryWrapper;
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;
import com.baomidou.mybatisplus.spring.service.impl.ServiceImpl;
import com.yourname.demo.entity.User;
import com.yourname.demo.mapper.UserMapper;
import org.springframework.stereotype.Service;

@Service   // 告诉 Spring：扫描我，把我放进容器
public class UserServiceImpl extends ServiceImpl<UserMapper, User> implements UserService {

    @Override
    public Page<User> pageList(long page, long size, String name, String email) {
        // 第 7 课的查询逻辑，原封不动从 Controller 搬过来
        LambdaQueryWrapper<User> wrapper = new LambdaQueryWrapper<>();
        wrapper.like(name != null && !name.isEmpty(), User::getName, name)
               .like(email != null && !email.isEmpty(), User::getEmail, email)
               .orderByDesc(User::getId);
        return page(new Page<>(page, size), wrapper);   // IService 自带的 page()
    }

    @Override
    public User createUser(User user) {
        save(user);   // IService 自带的 save()，对应 userMapper.insert(user)
        return user;
    }
}

extends ServiceImpl<UserMapper, User> 的两个泛型参数分别是：它要操作哪个 Mapper、操作哪个实体。继承之后，IService 的所有方法自动可用，内部会帮你调用 UserMapper -- 你一行实现都不用写。

@Service 与 Spring 容器：后端的 provide / inject

@Service 干的事和 @RestController（第 4 课）一样：Spring Boot 启动时扫描所有带这些注解的类，各创建一个实例放进"容器"（默认单例，全应用共享）。

这套机制用 Vue 类比再合适不过：

// Vue3 中
app.provide('userStore', userStore)   // ≈ @Service：注册进容器
const store = inject('userStore')     // ≈ 依赖注入：从容器取出使用

@Service 就是 @Component 的语义化版本，功能相同，名字标明"我是业务层"。

完全兼容

本课所有代码 -- 接口、继承、注解、构造器注入 -- 都是 Java 和 Spring 早期就有的基础特性，没有任何 JDK 9+ 语法，在 JDK 8 下原样可用。

MyBatis Plus 的 IService / ServiceImpl 在 JDK 8 环境（Spring Boot 2.x）同样可用，只需使用对应的 starter，对照表见第 6 课。

注意：import 路径因版本而异

MyBatis Plus 3.5.17 的 Spring Boot 4 starter 中，IService 和 ServiceImpl 的包路径从 com.baomidou.mybatisplus.extension.service 移到了 com.baomidou.mybatisplus.spring.service。本课代码示例已使用新路径。如果你用 Spring Boot 2.x（JDK 8），import 路径是旧的 extension.service。

第三步：重构 UserController

现在把 Controller 里的查询逻辑全部搬空，改成调用 Service。先看重构前（你现在的代码）：

@RestController
@RequestMapping("/users")
public class UserController {

    @Autowired
    private UserMapper userMapper;   // 直接操作 Mapper -- 今天要去掉

    @GetMapping
    public Page<User> getList(
            @RequestParam(defaultValue = "1") long page,
            @RequestParam(defaultValue = "10") long size,
            @RequestParam(required = false) String name,
            @RequestParam(required = false) String email) {
        Page<User> pageObj = new Page<>(page, size);
        LambdaQueryWrapper<User> wrapper = new LambdaQueryWrapper<>();
        wrapper.like(name != null && !name.isEmpty(), User::getName, name)
               .like(email != null && !email.isEmpty(), User::getEmail, email)
               .orderByDesc(User::getId);
        return userMapper.selectPage(pageObj, wrapper);
    }
    // ... 其他方法也都直接调用 userMapper
}

重构后 -- 每个方法只剩一行调用，干净清爽：

package com.yourname.demo.controller;

import com.yourname.demo.entity.User;
import com.yourname.demo.service.UserService;
import org.springframework.web.bind.annotation.*;
import com.baomidou.mybatisplus.extension.plugins.pagination.Page;

@RestController
@RequestMapping("/users")
public class UserController {

    private final UserService userService;

    // 构造器注入：Spring 启动时自动把容器里的 UserService 实例传进来
    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping
    public Page<User> getList(
            @RequestParam(defaultValue = "1") long page,
            @RequestParam(defaultValue = "10") long size,
            @RequestParam(required = false) String name,
            @RequestParam(required = false) String email) {
        return userService.pageList(page, size, name, email);
    }

    @GetMapping("/{id}")
    public User getById(@PathVariable Long id) {
        return userService.getById(id);
    }

    @PostMapping
    public User create(@RequestBody User user) {
        return userService.createUser(user);
    }

    @PutMapping("/{id}")
    public User update(@PathVariable Long id, @RequestBody User user) {
        user.setId(id);
        userService.updateById(user);
        return userService.getById(id);
    }

    @DeleteMapping("/{id}")
    public String delete(@PathVariable Long id) {
        userService.removeById(id);
        return "Deleted user " + id;
    }
}

注意三个变化：

  • UserMapper、LambdaQueryWrapper 的 import 全部消失 -- 查询条件是业务细节，归 Service 管，Controller 不该认识它们。
  • @GetMapping("/{id}") 等方法直接调 userService.getById(id) -- IService 自带的方法，ServiceImpl 已经帮你实现好了。
  • 字段注入 @Autowired private UserMapper 换成了构造器注入。

为什么推荐构造器注入？

之前课程用 @Autowired 标在字段上，能工作，但 Spring 官方推荐构造器注入：

  • final 字段 -- 依赖不可变，不可能被意外替换
  • 依赖关系一目了然 -- 看构造器就知道这个类需要什么
  • 方便测试 -- 单元测试时 new UserController(mockService) 就能传入 mock

而且只有一个构造器时，连 @Autowired 注解都不用写，Spring 自动识别。

第四步：加入第一个真正的业务逻辑 -- 邮箱查重

架构搭好了，现在体会一下 Service 层的价值。需求：新增用户时，邮箱不能重复。

想想这段逻辑放哪？放 Controller？那未来后台管理接口也要新增用户时就得复制一遍。这是典型的业务规则，放 Service：

// UserServiceImpl.java 中，修改 createUser 方法
@Override
public User createUser(User user) {
    // 业务规则：邮箱不能重复
    long count = count(new LambdaQueryWrapper<User>()
            .eq(User::getEmail, user.getEmail()));
    if (count > 0) {
        throw new IllegalArgumentException("邮箱已被注册: " + user.getEmail());
    }
    save(user);
    return user;
}

count(wrapper) 也是 IService 自带方法，对应 userMapper.selectCount(wrapper)，生成 SELECT COUNT(*) FROM users WHERE email = ?。整个方法读起来就是业务本身：查重 -> 重复就报错 -> 不重复才保存。

现在抛异常会发生什么？（下一课的钩子）

重启后测试：用同一个邮箱 POST 两次，第二次你会看到 Spring Boot 默认的 500 错误页（Whitelabel Error Page）-- 一堆 HTML 和服务器内部信息。你的 Vue3 前端 axios 收到的是 HTML 而不是 JSON，res.data 根本没法解析。

这就像前端把原始 Error 对象直接 alert() 给用户看。正确的做法是后端把所有异常统一转成规范的 JSON 错误响应 -- 这就是下一课：全局异常处理（@RestControllerAdvice）要解决的问题。今天先让业务规则生效即可。

IService 与 BaseMapper 方法对照

IService 的方法名和 BaseMapper 刻意不同（get 查单行、remove 删除、list 列表、page 分页），避免两层方法混淆。对照表：

操作 Mapper 层 BaseMapper Service 层 IService
新增 insert(entity) save(entity)
按 ID 删除 deleteById(id) removeById(id)
按 ID 更新 updateById(entity) updateById(entity)
按 ID 查询 selectById(id) getById(id)
条件计数 selectCount(wrapper) count(wrapper)
条件列表 selectList(wrapper) list(wrapper)
分页查询 selectPage(page, wrapper) page(page, wrapper)

更多方法见 MyBatis Plus 速查表。ServiceImpl 内部就是帮你调用对应的 BaseMapper 方法，所以 SQL 行为完全一致。

项目大了怎么组织包？

本课的 Service 文件放在 com.yourname.demo 下（和现有文件保持一致）。但类多了应该按层建子包：controller/、service/、mapper/、entity/、config/ -- 对应你前端的 src/components/、src/stores/、src/api/。详见 第 10 课：Java 包与项目结构。

小测验

"新增用户前检查邮箱是否重复"这类业务逻辑，应该放在哪一层？

  • Controller 层 -- 它最先收到请求
  • Service 层 -- 业务规则的归属地
  • Mapper 层 -- 离数据库最近查重最快
  • Entity 类里 -- 数据自己的规则自己管

小测验

@Service 注解的作用是什么？

  • 把这个类标记为对外提供 HTTP 接口
  • 让 Spring 扫描并为它创建实例放进容器，供其他类注入
  • 自动为这个类生成全部业务方法的实现
  • 把这个类注册为数据库表对应的实体

小测验

UserServiceImpl 继承 ServiceImpl<UserMapper, User> 之后，获得了什么？

  • 只是代码风格约定，没有实际功能
  • 自动生成了 Controller 层的 HTTP 接口
  • IService 自带的全套 CRUD 方法，内部自动调用 UserMapper
  • 数据库连接池和事务管理能力
